# Подключение лид-бота к LeadChat

Готово со стороны бота на 12.08.2026. Здесь — контракт, настройки, готовый адаптер
для стороны LeadChat и список того, что нужно решить перед боевым включением.

## 1. Куда именно встаём

У движка сценариев LeadChat (`app/bots/engine.py`) поставщик ответов подключается через
маленький протокол:

```python
async def ai_answer(bot, dialog, item_title) -> {"reply","confidence","needs_operator"} | None
async def classify_message(texts) -> dict | None
```

Это и есть шов. LeadChat перестаёт ходить в модель напрямую и спрашивает нас — а мы отвечаем
уже по регламенту: роутеры (отказы, согласования, жалобы, статусы, мусор), RAG на живых
диалогах, ценовая лестница, гарды воронки и стиля. Правила сценария (`send`, `ask`, `menu`,
`condition`, таймауты, теги) остаются за LeadChat: мы отвечаем только за содержание реплики
и за решение «этого клиента дальше ведёт человек».

**Что мы НЕ берём на себя:** доставку в Авито, состояние диалога, расписание бота, теги и
заметки. Мы — чистая функция «переписка → следующая реплика мастера».

## 2. Эндпоинт

```
POST https://<хост-бота>/api/leadchat/answer
Authorization: Bearer <LEADBOT_SERVICE_TOKEN>
Content-Type: application/json
```

Запрос:

```json
{
  "request_id": "conv42:msg1007",
  "dialog": [
    {"role": "user",      "content": "Холодильник не морозит"},
    {"role": "assistant", "content": "Здравствуйте, какая марка?"},
    {"role": "user",      "content": "Атлант, лет пять"}
  ],
  "item_title":  "Ремонт холодильников на дому",
  "client_name": "Анна",
  "city":        "Ульяновск",
  "persona":     "Марк",
  "direction":   "",
  "partner":     "",
  "white":       false
}
```

| Поле | Обязательно | Зачем |
|---|---|---|
| `dialog` | да | Вся видимая переписка. `user` — клиент, всё остальное — наши прошлые реплики. Нужна хотя бы одна реплика клиента |
| `request_id` | нет, но очень желательно | Идемпотентность: повтор с тем же значением вернёт прежний ответ и не потратит вызов модели. Годится `«conv<id>:msg<id>»` |
| `item_title` | нет | Название объявления — направление и цены зависят от него |
| `client_name` | нет | Обращение по имени |
| `city` | нет | Территория, прайс-колонка, время выезда. Берите из `avito_accounts.city` или из ссылки объявления |
| `persona` | нет | Имя мастера. **Передавайте всегда**: без него модель придумывает имя, и в разных диалогах оно разное |
| `direction` | нет | `bt` / `kp` / `mnc`. Пусто — определим сами по тексту |
| `partner`, `white` | нет | Партнёрская схема и «белый» аккаунт (там свой пол цены) |

Ответ (всегда 200, кроме 401 и 400):

```json
{
  "reply": "да, помогу. Какая модель холодильника?",
  "confidence": 0.9,
  "needs_operator": false,
  "meta": {"layer": "claude-haiku-4-5", "flag": null, "missing": ["phone"],
           "ready": false, "ms": 2610, "request_id": "conv42:msg1007"}
}
```

`reply`, `confidence`, `needs_operator` — ровно то, что ждёт `exec_ai_answer`. `meta`
движку не нужна, но её стоит писать в лог: `layer` показывает, кто ответил (роутер или
модель), `flag` — сработавшее правило регламента, `missing` — чего не хватает до заявки.

## 3. Как читать наш ответ

Мы подстроились под то, как ваш движок уже устроен:

| Наш случай | Что вернём | Что сделает движок |
|---|---|---|
| Обычный ответ | текст, `confidence` 0.9–1.0, `needs_operator: false` | отправит клиенту, пойдёт по `next` |
| Мостик и человеку (статус визита, «уже наш клиент») | текст, `needs_operator: true` | отправит текст, затем handoff |
| Молча человеку (жалоба, претензия) | пустой `reply`, `needs_operator: true` | handoff без реплики |
| Таймаут, падение, плохой запрос | пустой `reply`, `needs_operator: true`, причина в `meta.reason` | handoff |

Уверенность мы **никогда** не занижаем у готового ответа: у вас при `confidence < 0.6`
текст выбрасывается и диалог уходит человеку. Роутеры (детерминированы) — `1.0`, модель — `0.9`.

Таймаут держим сами: `LEADBOT_ANSWER_TIMEOUT_S` (по умолчанию 9 секунд) — заведомо раньше
вашего `AI_TIMEOUT_SECONDS` (10). Так решение о передаче человеку принимаем мы и осмысленно,
а не ваш секундомер.

## 4. ⚠ Телефоны слать в СЫРОМ виде

`load_dialog_for_ai` у вас маскирует номера (`mask_phones`) — это правильно, когда запрос
уходит за границу через прокси. **К нам это не относится:** мы свой сервис в том же контуре,
запрос никуда не уезжает. А без живого номера наша воронка не видит, что телефон уже получен,
и просит его снова и снова — самый заметный признак бота.

Поэтому адаптер шлёт **немаскированный** текст. Если в диалоге встретится `{PHONE}`, мы
вернём предупреждение в `meta.warnings`, но исправить это на своей стороне не сможем.

## 5. Настройка

На стороне бота (в `/etc/leadbot.env`):

```
LEADBOT_SERVICE_TOKEN=<длинная случайная строка>
LEADBOT_ANSWER_TIMEOUT_S=9
```

Токен служебный и отдельный от `LEADBOT_PANEL_TOKEN`: панельный секрет открывает всю
переписку и настройки, чужому сервису его давать нельзя. Без `LEADBOT_SERVICE_TOKEN`
эндпоинт закрыт наглухо и отвечает 401.

Проверка живьём:

```
curl -sS -X POST https://<хост-бота>/api/leadchat/answer \
  -H "Authorization: Bearer $LEADBOT_SERVICE_TOKEN" -H 'Content-Type: application/json' \
  -d '{"request_id":"smoke-1","dialog":[{"role":"user","content":"Холодильник не морозит"}]}'
```

## 6. Адаптер для стороны LeadChat — уже написан

Файл создан в их репозитории: **`app/bots/leadbot_provider.py`**. Движок принимает бэкенд
параметром `ai=`, а воркер прокидывает его через `ctx["bot_ai"]`
(`app/bots/runtime.py::_engine_kwargs`) — поэтому сам движок править не пришлось.

Подключение тоже сделано, в `app/workers/main.py::startup`:

```python
if settings.leadbot_url and settings.leadbot_token:
    from app.bots.leadbot_provider import LeadbotAI
    ctx["bot_ai"] = LeadbotAI(settings.leadbot_url, settings.leadbot_token)
```

Пусто в настройках — работает как раньше, через `app.bots.ai`. Заполнено — шаг `ai_answer`
спрашивает лид-бота. Переключение обратимо одной переменной окружения.

В `app/core/config.py` добавлены два поля: `leadbot_url` и `leadbot_token`.

Адаптер собирает диалог **без маскировки телефонов** — см. §4, это осознанное отличие от
`load_dialog_for_ai`. И пишет в лог три вещи, которые движку не нужны, а очереди людей
обязательны: причину эскалации со сроком, событие «лид готов» и предупреждения бота.

## 6.1. Что лежит в `meta` сверх контракта движка

```json
"meta": {
  "layer": "локальный роутер (эскалация: status)",
  "escalation": {"reason": "status", "label": "вопрос о статусе визита",
                 "deadline_min": 10, "note": "Вас ждать?"},
  "lead_ready": false, "lead": null,
  "missing": ["phone"], "ms": 2, "request_id": "conv42:msg1007"
}
```

**`escalation`** — почему диалог отдан человеку и за сколько минут на него надо ответить.
Срок разный по причинам, потому что три четверти очереди срочные по природе. Источник
истины — `brain/escalation.py` (`REASONS` и `DEADLINES`); таблица ниже собрана из него:

| Причина | Слаг | Срок |
|---|---|---|
| Срыв визита | `no_show` | 5 мин |
| Модель не ответила — клиенту не ушло ничего | `model_silent` | 10 мин |
| Вопрос о статусе визита | `status` | 10 мин |
| Тема не распознана | `unknown_topic` | 10 мин |
| Клиент просит позвонить | `call_request` | 15 мин |
| Претензия к работе или деньгам | `claim` | 15 мин |
| Недовольство с агрессией или после работы | `discontent` | 15 мин |
| Сомнение в предыдущем мастере — проверить нельзя | `prior_master` | 20 мин |
| Модель не справилась и позвала человека | `model_handoff` | 30 мин |
| Перенос или сдвиг времени | `reschedule` | 30 мин |
| Тема по согласованию — обещали вернуться с ответом | `soglasovanie` | 30 мин |
| Отказ от заявки | `cancel` | 120 мин |
| Тема вне ремонта — бот отказал сам | `offtopic` | 120 мин |
| Три хода не по делу — разговор закрыт | `troll_exit` | 120 мин |
| Профиль из чёрного списка — отвечать не нужно | `blocklist` | 240 мин |
| Один профиль более чем на 5 наших аккаунтах — сливаем | `multi_account` | 240 мин |

⚠ **Причина обязана быть настоящей.** Замер боевого журнала воронки 23.08: 194 передачи
человеку из 194 приходили с ярлыком «тема не распознана», хотя код, отдавший диалог, причину
знал точно — закрытый филиал, село за чертой города, нет филиала направления. Слаг задаёт срок
реакции, по которому работает сторож просрочки, поэтому один слаг на всё означал и один срок
на всё. Место, где причина назначается, — `server._передать(res, причина)`; сторож набора
`analysis/test_escalation_reason.py` не даёт вернуть передачу без причины.

**`lead_ready` и `lead`** — заявка собрана: телефон есть, окно предложено. Это **не**
эскалация. Такие диалоги обязаны идти в отдельную очередь на подтверждение времени, потому
что календаря у бота нет и слот ничем не подтверждён. Если смешать их с претензиями, очередь
недовольств утонет в успешных заявках и перестанет что-либо показывать.

## 6.2. Что уже включено (12.08, проверено живьём)

Сделано так, а не как предлагалось выше: бот по-прежнему слушает `127.0.0.1:8788`, а в
туннель выходит **отдельной дверью в Caddy** — `10.10.0.2:8790`, где открыт ровно один
путь `/api/leadchat/answer`. Панель и остальной API в туннель не видны, наружу порт
закрыт (`bind 10.10.0.2` — сайт-адрес в Caddy только сопоставляет, слушать заставляет
именно `bind`; проверено `nc -z` снаружи). Это лучше, чем `LEADBOT_HOST=10.10.0.2`:
тот вариант выставил бы в туннель **весь** сервис вместе с панелью.

| Сторона | Что стоит |
|---|---|
| Бот, `/etc/leadbot.env` | `LEADBOT_SERVICE_TOKEN=<24 байта hex>`, `LEADBOT_ANSWER_TIMEOUT_S=9`, `LEADBOT_HOST` не тронут |
| Бот, Caddy | `10.10.0.2:8790` → `127.0.0.1:8788`, только `/api/leadchat/answer` |
| LeadChat, `/srv/leadchat/.env` | `LEADBOT_URL=http://10.10.0.2:8790`, `LEADBOT_TOKEN=<тот же токен>` |

Сквозная проверка из Петербурга: обычный ответ за 1972 мс, вопрос «Вас ждать?» —
эскалация с причиной `status` и сроком 10 минут, запрос без токена — 401.

**Осталось два шага:** перезапустить воркер LeadChat (пока провайдер в его процессе не
поднят) и в сценарии бота поднять `context_messages` с 10 до **30** (потолок их схемы) —
замер показал +167 входных токенов на вызов при 45 000 из кэша, то есть шум, а замок
состояния и качество ответов от этого выигрывают.

## 6.3. Режим бота в LeadChat: сначала подсказка

В LeadChat у бота теперь есть режим (миграция `0035`, поле `bots.mode`):

* **`suggest` — подсказка оператору.** Бот считает ответ по регламенту и кладёт его
  заметкой в диалог: `Подсказка бота: …`. Клиент **не получает ничего**, отвечает человек.
* **`auto` — автоответ.** Текст уходит клиенту в Авито, как и раньше.

Умолчание — `suggest`, и это осознанно: на живом аккаунте сначала должно быть видно, ЧТО
бот пишет, и лишь потом ему отдают слово. Переключение — в редакторе бота, вместе с
сохранением сценария (не отдельной кнопкой: режим меняют вместе с правкой текстов, и
применять его раньше «Сохранить» значит выпустить к клиенту недоделанный сценарий).

Для нас режим прозрачен: контракт `/api/leadchat/answer` от него не зависит, мы всегда
отвечаем одинаково. Разница только в том, что делает с нашим текстом их движок. Но
именно этот режим и есть безопасный способ включить бота на первом боевом аккаунте:
неделя в подсказках даёт корпус реальных пар «клиент — предложенный ответ» без единого
риска для клиента.

⚠ Одно следствие для очередей: в режиме подсказки «мостик + человеку» (наш текст +
`needs_operator`) превращается в **две заметки подряд** — сам ответ и передачу человеку.
Клиент по-прежнему не видит ничего.

## 7. Что осталось решить

1. **Сеть — единственная настоящая работа, и она маленькая.** Бот живёт на <IP наблюдателя>,
   прод LeadChat — на <IP прода>. Приватный мост WireGuard между ними **работает в обе
   стороны** (проверено 12.08: интерфейс `wg0`, бот — `10.10.0.2/24`, пир `10.10.0.1`,
   свежий handshake, keepalive 25 с, трафик идёт в обоих направлениях). Односторонняя там
   только авторизация ssh-ключей — к HTTP это отношения не имеет.

   Мешает другое: бот слушает **только `127.0.0.1:8788`** (`LEADBOT_HOST=127.0.0.1` в
   `/etc/leadbot.env`), поэтому из туннеля до него не достучаться. Нужно одно из двух:
   - `LEADBOT_HOST=10.10.0.2` в `/etc/leadbot.env` и рестарт — бот станет виден по
     `http://10.10.0.2:8788/api/leadchat/answer` **только внутри туннеля**, наружу порт
     закрыт (он не проброшен в Caddy);
   - либо оставить локальный бинд и добавить в Caddy отдельный маршрут на адрес туннеля.

   Первый вариант проще и не открывает эндпоинт в интернет. Токен всё равно обязателен:
   туннель — это транспорт, а не аутентификация.
2. **Параллельность.** Шлюз модели пускает 2 запроса разом. На потоке 1500 диалогов в
   сутки этого хватает, на пиковых 60/час — стоит замерить.
3. **Кто говорит первым.** У нас есть свой ответ на голое «Здравствуйте» (роутер, 0 токенов);
   если в сценарии стоит шаг `send` с приветствием, они наложатся.
4. **Семь тем без регламента** (геймпады, провайдер, фасады, торговый холод, пружины,
   iMac, спутниковое) — на них бот отвечает наугад. Список с цифрами по живому корпусу —
   в `~/Work/leadbot-разбор-12.08/HANDOFF.md`.
5. **Ключ API** помечен как засветившийся, перевыпустить до боевого потока.
